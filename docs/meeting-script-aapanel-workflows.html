Two workflows, one rule: edit WordPress in aaPanel, never on live static

Read this out. Pause at the blue boxes. You can skip a sentence if the room is already nodding.

Thanks everyone. I just want us on the same page for how we edit sites and how we convert a WordPress site to static. Nothing fancy. Two paths, same idea.

If the live site is already static, we do not type into production. We restore WordPress in aaPanel on dev.domain.com, edit there, then scrape to static when it is ready.

If the live site is still WordPress, we still use aaPanel for the staging copy when we can, so production stays calm while we fix things.

Workflow 1 — live site is already static

You say

This is the everyday edit path. Production stays static. Visitors keep seeing the live site while we work.

  1. Restore the latest WordPress backup in aaPanel.
  2. Put it on dev.domain.com in aaPanel.
  3. Edit and fix there. Blogs, SEO, layout, forms. Not on the live static site.
  4. Backup that edited WordPress in aaPanel so we do not lose the work.
  5. Audit the WP subdomain. If it fails, stay in aaPanel and fix. Do not scrape yet.
  6. When WP passes, scrape to static.domain.com.
  7. Compare WP staging vs static staging. Same pages, forms, SEO, mobile.
  8. Audit static. If it fails, scrape again from the good aaPanel copy. Do not push live.
  9. Compare static staging vs live static production, so we know what will change.
  10. Push to production. Keep the previous version for rollback.
  11. Quick live check: pages, forms, images, SSL. Then we are done.

The loop is simple. Fail on WordPress? Fix in aaPanel. Fail on static? Scrape again. Live does not move until both audits pass.

Ask the room

Any reason we would still edit a live static site directly? If not, we lock this: aaPanel only for WordPress edits.

Workflow 2 — live site is still WordPress

You say

Same spirit, first conversion. Production is still WordPress until we cut over.

We audit live WordPress first. Fixes can happen on a copy in aaPanel staging so we are not experimenting on the public site if we can avoid it. If a small fix must be on live WP, we still backup first.

  1. Audit the live WordPress site.
  2. Edit and fix in aaPanel staging when possible. Re-audit until it passes.
  3. Backup the approved WordPress. aaPanel for the staging copy. Keep the usual production backup too.
  4. Create static.domain.com if it is not there yet.
  5. Scrape WordPress to that static subdomain.
  6. Audit static. Fail? Scrape again. Do not switch apex.
  7. Compare static vs live WordPress so nothing important is missing.
  8. Approval: scan, human look, comparison all pass.
  9. Then we switch production to static.
  10. Post-deploy check on the live domain.

After that cutover, future edits use Workflow 1. We do not keep editing production WordPress once the site is static.

Ask the room

For first conversions, are we good that live WordPress stays up until static. has passed audit?

What we are not doing

You say

Quick don’ts, so nobody gets surprised later.

  • We do not roll a live static site back to WordPress just to change a blog post.
  • We do not edit KV or static HTML by hand.
  • We do not scrape “because it has been a while.” We scrape when the aaPanel edit is ready.
  • We do not stand up a new Worker per site. Fleet Worker only.
